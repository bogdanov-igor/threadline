# Из сваггера в файл

Здесь точный порядок действий: что взять из документа, куда положить и как проверить.

> Главное правило: не угадывать. Чего в документе нет или что в нём противоречит, в файл не идёт, а идёт в список вопросов. Неточное название только выглядит плохо, а неверное правило итога красит хорошие запросы в красный или прячет настоящие ошибки.

## Шаг 1. Соберите материалы

| Что нужно | В каком виде |
|---|---|
| Описание API | OpenAPI или Swagger, коллекция Postman, WSDL |
| JSON-RPC и SOAP без сваггера | Адрес, список действий, пример запроса и ответа |
| Ошибки | Таблица: код, HTTP-статус, текст, что делать |
| Статусы операций | Перечисление или таблица: значение и его смысл |
| Критерий успеха | Фраза «что считается успехом», примеры успешного и ошибочного ответа |
| Хосты | Адреса системы по средам |

Настоящих данных клиентов в материалах быть не должно: ни логов, ни тел ответов, ни номеров карт, ни имён, ни телефонов, ни токенов. Нашли такое: файл не обрабатывайте и сообщите владельцу проекта.

## Шаг 2. Скачайте текущий файл

Откройте «Файл проекта» и нажмите «Скачать». Из него видно, какие системы и типы id уже есть. Типы id из него повторять не нужно.

Одна система: один файл. Файл применяется целиком, поэтому плохой файл держит только себя.

## Шаг 3. Решите, чья это система

- Сваггер описывает то, что вызывают у вас: это система проекта, `kind: project`, `key` равен идентификатору проекта.
- Сваггер описывает то, что вызываете вы: это внешняя система, `kind` не пишется.
- Неясно: вопрос в список.

## Шаг 4. Перенесите поля

| Откуда в сваггере | Куда в файле | Как |
|---|---|---|
| `info.title` | `key`, `name` | `key`: строчная латиница, цифры, дефис. Один раз и навсегда |
| `servers[].url` | `hosts` | Только хост и порт. `https://gateway.pay.example:8443/gw/v2` даёт `gateway.pay.example:8443`. Порта нет: хост без порта. Шаблоны с `{env}`, `localhost` и `example.com` не берите |
| `servers[].url`, путь | начало `path` | В `path` полный путь, как в логе: `/gw/v2` и `/payments` дают `/gw/v2/payments` |
| `paths` и HTTP-метод | `http`, `path` | Своя запись на каждую пару. `'*'` только если HTTP-метод не назван |
| `summary` | `name` | По-русски, до 80 символов. Нет `summary`: первая фраза `description`, затем `operationId`, затем путь и вопрос в список. У `deprecated` метод остаётся, в названии «(устарел)» |
| `tags[0]` | `domain` | До 40 символов |
| `description` | `description` | До 500 символов, без примеров |
| Таблица ошибок, `responses` | `errors` | Шаг 5 |
| Фраза о том, что считать успехом | `outcomes`, `description` системы | Шаг 6 |
| Перечисление статусов | `idTypes[].statuses`, `methods[].status` | Шаг 7 |

Не переносите `example`, `examples`, `default`, `securitySchemes`, заголовки.

**JSON-RPC и SOAP.** Путей нет, действие в теле. Каждое действие это своя запись: `http: POST`, `path` это адрес, `/` для корня, `rpc` это поле `method` у JSON-RPC или первый элемент `Body` без префикса у SOAP. У входа в сам проект действие не читается.

**Что шаблоном не записать.** `/files/{name}.json` и `/users/{id}:activate`: подстановка занимает часть пути целиком. Это вопрос в список.

## Шаг 5. Ошибки

Для каждой строки таблицы ошибок:

1. `code`: код из таблицы, в кавычках.
2. `text`: различимая подстрока от 3 символов, только если кода нет.
3. `title`: текст по-русски.
4. `action`: только из документа.
5. `partnerCode`: только по таблице соответствия.
6. Сказано об одном методе: добавьте `method`.

Правило ошибки работает, только если ответ уже считается ошибкой. Проверьте это на шаге 6.

## Шаг 6. Итог ответа

Это самый важный шаг. Отвечайте на вопросы по порядку.

1. **Есть прямая фраза или пример ответа: что успех, что ошибка?** Нет: правила нет, вопрос в список.
2. **Что решит Threadline без правила?** Ошибка, если HTTP 400 и выше или в теле общий признак. Список: «Правила итога». Иначе успех.
3. **Совпало с документом?** Правило не нужно.
4. **Не совпало?** Пишите правило. Условия узкие: HTTP-статус и поле вместе.
5. **Какой уровень?** Самый узкий. Сказано о методе: `method`. Сказано обо всех методах системы: система. `general` только если так решил владелец проекта.
6. **Какой итог?** `success`: операция удалась. `error`: нет. `pending`: ещё идёт. `ignore`: ответ отрицательный, но это норма.

| Ответ | Что сказано в документе | Без правила | Что пишем |
|---|---|---|---|
| 200 `{"status":"OK"}` | OK это успех | успех | ничего |
| 200 `{"status":"OK","error":{"code":0,"message":"none"}}` | OK это успех, `error` есть всегда | ошибка | система: `http: 200`, `status = OK`, `success` |
| 200 `{"status":"error","message":"Limit exceeded"}` | `error` это отказ, текст в `message` | успех | система: `http: 200`, `status = error`, `error`, `text: '{message}'` |
| 200 `{"resultCode":"51"}` | 51: нет средств | успех | система: `http: 200`, `resultCode = '51'`, `error`, текст |
| 422 `{"status":"OK"}` у `/check` | для этого метода норма | ошибка | метод: `http: 422`, `status = OK`, `success` |
| 404 у поиска клиента | «не найден» это штатный ответ | ошибка | метод: `http: 404`, `ignore` |
| 200 `{"error":{"code":"00","message":"Approved"}}` | 00 это успех | ошибка | `errors`: `code: '00'`, `severity: ok` |
| 202 `{"state":"PROCESSING"}` | ещё обрабатывается | успех | метод: `http: 202`, `state = PROCESSING`, `pending` |

## Шаг 7. Id и операции

1. Какие бизнес-операции есть: платёж, перевод, заявка? Каждая это тип `kind: operation`.
2. Id в пути: назовите подстановку по типу. `{id}` переименуйте в `{paymentId}`, если документ говорит, чей это id.
3. Id в теле или строке запроса: добавьте `fields`.
4. Какой метод создаёт операцию: `kind: start`. Какой отдаёт статус: `kind: status`. Входящий колбэк: `kind: callback`, только у системы проекта. Им всем нужен `op`.
5. Перечисление статусов: словарь `statuses` по порядку жизни. Смысл значения не описан: не вносите, вопрос в список.
6. Значения в ответе отличаются от словаря: добавьте `map`.
7. Правило итога из словаря не выводите.

## Шаг 8. Запишите вопросы

Рядом с файлом ведите список, строка на вопрос: метод или код, что неясно, файл и раздел документа, варианты, если видны. Без настоящих значений.

| Случай | Что делать |
|---|---|
| Документы расходятся в пути, HTTP-методе или коде | Записи нет |
| У кода два смысла | Записи нет. Смысл зависит от метода и это сказано прямо: правила методов |
| Не сказано, что считать успехом | Правил итога нет. Методы и ошибки заводите |
| Описание и пример ответа расходятся | Правил итога нет |
| Значение статуса без смысла | Значения в словаре нет |
| Форма не выражается: массив, часть пути | Записи нет |

Остальное из документа загружается. Список отдаётся владельцу проекта, ответы идут в новую версию файла.

## Пример целиком

Сваггер партнёра:

```yaml part
openapi: 3.0.3
info:
  title: Pay Gateway
  description: 'Успех: HTTP 200 и status = OK. Отказ: HTTP 200, status = error, код в error.code, текст в error.message. Поле error есть всегда, при успехе его code равен 0.'
servers:
  - url: https://gateway.pay.example:8443/gw/v2
paths:
  /payments:
    post:
      summary: Создание платежа
      tags: [Платежи]
  /payments/{id}:
    get:
      summary: Статус платежа
      tags: [Платежи]
      description: Поле data.state, значения CREATED, PAID, DECLINED.
```

Таблица ошибок из документа: `error.code = 51`, недостаточно средств, предложить другую карту.

Готовый файл:

```yaml full
version: 1
project: acme
idTypes:
  - key: payment
    kind: operation
    name: Платёж
    statuses:
      - { value: CREATED, name: Создан, outcome: pending }
      - { value: PAID, name: Оплачен, outcome: success }
      - { value: DECLINED, name: Отклонён, outcome: failure }
systems:
  - key: pay
    name: Pay Gateway
    hosts:
      - gateway.pay.example:8443
    description: 'Успех: HTTP 200 и status = OK. Отказ: HTTP 200, status = error, код в error.code. Поле error есть всегда'
    methods:
      - http: POST
        path: /gw/v2/payments
        name: Создание платежа
        domain: Платежи
        kind: start
        op: payment
      - http: GET
        path: /gw/v2/payments/{paymentId}
        name: Статус платежа
        domain: Платежи
        kind: status
        op: payment
        status: { in: response, path: data.state }
    errors:
      - code: '51'
        title: Недостаточно средств
        action: Предложите клиенту другую карту
    outcomes:
      - when:
          http: 200
          fields:
            - { path: status, equals: OK }
        outcome: success
```

Что здесь решено и почему:

- `path` начинается с `/gw/v2`: так адрес выглядит в логе.
- `{id}` стал `{paymentId}`: документ говорит, что это платёж.
- Правило `status = OK` нужно: поле `error` есть всегда, и без правила успешный ответ был бы красным.
- Правила на `status = error` нет: непустое `error` и так считается ошибкой. Такой ответ совпадает с документом, а код 51 называет правило ошибки.
- `action` взят из таблицы ошибок. Там, где его нет, поля нет.

## Что нельзя и что взять в кавычки

- Настоящих значений в файле нет: ни номеров карт, ни телефонов, ни имён, ни токенов, ни id, ни сумм, ни тел ответов.
- Поля `password`, `token`, `pin`, `cvv`, `pan`, `phone`, `passport`, `accountId` и подобные не годятся для id, статуса, `{путь}`, `equals`, `oneOf` и `regex`. Для них можно только `exists`.
- В кавычки берите `'*'`, `code`, цифровые `value` и `partnerCode`, `equals` с ведущими нулями, `text` с `{путь}`, шаблон хоста со звёздочкой и всё, где после двоеточия идёт пробел.

## Как проверить файл

При переносе легко ошибиться, даже когда текст выглядит хорошо. Проверка обязательна.

1. **Вставьте файл на страницу.** Нажмите «Загрузить файл» или вставьте текст. Проект от этого не меняется.
2. **Исправьте ошибки по путям из проверки.** Что значит каждая: «Сообщения проверки». Предупреждения тоже прочитайте: они называют поля, которые не действуют.
3. **Сверьте числа.** Методов в «Будет добавлено» столько же, сколько в сваггере минус вопросы.
4. **Проверьте «Будет изменено».** Каждую строку. Если системы уже есть, файл не должен стирать `hosts` и другие поля.
5. **Проверьте «Будет скрыто».** Там не должно быть ничего, что вы не собирались скрывать.
6. **Проверьте правила итога глазами.** У каждого должна быть фраза в документе. Правило `http: 200` с `success` без поля: удалите сразу.
7. **Проверьте тексты.** `title` и `action` взяты из документа, а не придуманы.
8. **Проверьте вопросы.** Пустой список при большом сваггере подозрителен.
9. **Примените.** Без «Заменить ручные правки»: правки аналитиков останутся.
10. **Проверьте на логах.** Поищите за тот же период, откройте запрос, посмотрите блок «Итог». Затем откройте раздел «Неизвестное» справочника: сверху самое частое, что ещё не описано.

Файл можно писать в редакторе со схемой формата: кнопка «Схема формата» на странице файла, сохраните её как `catalog.schema.json`. Схема ловит форму записи, но не всё: ссылки на типы id, диапазон HTTP, разбор `regex`, ключ системы проекта и номер карты в тексте проверяет только сервер. Поэтому шаг 1 нужен и при зелёной схеме.

## Раздел «Неизвестное»

Здесь всё, что Threadline встретил в логах и не узнал. Адрес вида `/acme/catalog/unknown`.

| Строка | Что значит | Как закрыть |
|---|---|---|
| Метод | Вход проекта или метод узнанной системы не описан | `methods` этой системы |
| Хост | Вызов на хост без системы | `hosts` новой или существующей системы |
| Ошибка | У узнанной системы нет правила | `errors` или правило итога |

Строка уходит сама, как только запись её покрывает. Правило итога с условием на поле строку не убирает: новые случаи перестают копиться, а строку после проверки скройте кнопкой «Скрыть».

Рабочий цикл такой: применить файл, поискать за тот же период, взять верх «Неизвестного», найти в документации. Нет в документации: вопрос в список.
