# Правила итога

Правило итога решает, чем кончился ответ: успехом, ошибкой, обработкой или штатным отказом. Это самое сильное правило файла: оно красит шаг и меняет статус запроса.

## Почему HTTP-код ничего не гарантирует

Разные системы отвечают по-разному.

- Ответ HTTP 200 бывает ошибкой: `{"status":"error","message":"Limit exceeded"}`.
- Ответ HTTP 422 бывает успехом: система так отвечает на штатную проверку.
- Ответ HTTP 404 бывает нормой: клиента просто нет.
- Ответ HTTP 200 с заполненным полем `error` бывает успехом: система пишет это поле всегда.

Threadline не может угадать это сам. Без правил он смотрит на общие признаки. С правилом верит правилу.

## Что будет без правила

Ответ считается ошибкой, если выполнено что-то одно:

- HTTP 400 и выше;
- в теле есть признак ошибки: непустое `error`, `result = error`, `success = false`, `res ≠ 0` вместе с `error`, `result_code` не `GOOD`, `transStatus = N`, `resultInfo.code ≠ 0`, `actionCode ≠ 000` у элемента с `type = card` в `statuses.item`, в XML `response_code ≠ 0` или `actionCode ≠ 000` у карты.

Иначе ответ считается успехом. Если вашей системе этого достаточно, правило не нужно.

## Как решается итог

![Как решается итог: сначала правила итога, затем общие признаки, затем правила ошибок](diagram:file-outcome)

Правило итога проверяется первым. Если оно подошло, общие признаки ошибки и важность правила ошибки на этот ответ больше не влияют.

Правила проверяются на ответах вызовов и на ответе проекта на вход. На записях приложения и на отправках без ответа они не проверяются. У базы данных и шины ответа нет: файл применится, а проверка предупредит, что правило не сработает.

Если сама запись ответа сделана с уровнем WARNING и выше, причина по уровню останется: правило итога её не снимает.

## Поля

| Поле | Обязательно | Что писать |
|---|---|---|
| `when` | да | Условия: `http`, `fields` или оба. Подходит, если выполнены все |
| `outcome` | да | `success`, `error`, `pending` или `ignore` |
| `text` | нет | Свой текст или шаблон с `{путь}`, в кавычках, до 200 символов |
| `action` | нет | «Что делать», до 500 символов, без подстановок |
| `priority` | нет | Порядок внутри уровня от 1 до 1000. Меньше раньше. По умолчанию 100 |
| `method` | нет | Ссылка на метод этой системы. Только в `systems` |
| `hidden` | нет | `true`: правило не действует |

`text` виден в блоке «Итог», а у `error` ещё в причине ошибки и на схеме. `action` виден в строке «Что делать». `when` и `priority` на экране не видны.

## Что значит каждый итог

| `outcome` | Что значит | Шаг | Запрос |
|---|---|---|---|
| `success` | Операция удалась | Зелёный, «успешно · по правилу итога системы» | Причины ошибки нет |
| `error` | Операция не удалась | Красный, текст правила | Статус «ошибка» |
| `pending` | Ещё идёт | Нейтральный с часами, «в обработке» | Не ошибка |
| `ignore` | Ответ отрицательный, но это норма | Не красный, «по справочнику не ошибка» | Не ошибка |

В блоке «Итог» панели шага видна пометка, какое правило решило: «по правилу итога метода», «системы» или «проекта».

![Блок «Итог» в панели шага: «ошибка · по правилу итога метода · HTTP 200», текст с подстановкой из тела ответа и «Что делать»](shot:file-outcome-step)

## Условия

### HTTP-статус

| Запись | Подходит к |
|---|---|
| `http: 200` | 200 |
| `http: [200, 202]` | 200 и 202 |
| `http: { from: 400, to: 499 }` | от 400 до 499 включительно |
| `http: [200, { from: 400, to: 499 }]` | 200 и от 400 до 499 |

В списке до 20 элементов.

### Поле тела

Условие на поле состоит из места, пути и ровно одной проверки.

| Проверка | Что значит | Пример |
|---|---|---|
| `equals` | Равно. Без пробелов по краям и без учёта регистра. `2` и `'2'` равны, а `'00'` и `0` нет | `{ path: status, equals: OK }` |
| `oneOf` | Одно из значений, до 50 | `{ path: state, oneOf: [NEW, PROCESSING] }` |
| `exists` | `true`: поле есть и не `null`. `false`: поля нет или оно `null` | `{ path: data.id, exists: true }` |
| `regex` | Выражение по значению поля, до 200 символов. Читаются первые 1000 символов значения | `{ path: message, regex: '^Timeout' }` |

Место `in`: `response`, это тело ответа и значение по умолчанию, или `request`, это тело отправки этого вызова.

Условий на поля в одном правиле до 10.

**Путь поля.** В JSON имена через точку по объектам: `data.transfer.state`. Заходить в массив нельзя: `items.0.state` не сработает.

В XML это локальное имя первого такого элемента, без префикса: `response_code` найдёт `<ns2:response_code>`. Если в пути есть точки, берётся последнее имя.

Ответ простым текстом или статус внутри массива правилом не выразить.

**Выражение `regex`.** Регистр учитывается. Чтобы не учитывать, начните с `(?i)`: `(?i)timeout`. Флаги пишутся только в начале: `(?i)`, `(?s)` или `(?is)`. Просмотр вперёд и назад и обратные ссылки запрещены.

## Текст правила

В `text` можно подставить значения из тела ответа: `{путь}`. До пяти мест. Берите текст в кавычки.

```yaml part
text: 'Отказ партнёра: {error.message}'
```

Что бывает при подстановке:

- Поля нет, или в нём объект или массив: на этом месте пусто.
- Готовый текст обрезается до 200 символов.
- Номера карт и другие скрытые значения показываются маской.

Если у правила с `error` текста нет или он вышел пустым, берётся текст правила ошибки, затем текст признака, затем `HTTP 500`. «Что делать» правила итога сильнее «Что делать» правила ошибки.

Ошибка с текстом правила не попадает в «Неизвестное».

## Уровни и порядок

Уровни те же, что у ошибок.

| Уровень | Где лежит | К чему относится |
|---|---|---|
| Метод | `systems[].outcomes[]` с полем `method` | Только этот метод |
| Система | `systems[].outcomes[]` без `method` | Все методы системы |
| Проект | `general.outcomes[]` | Все системы, в том числе неузнанные |

Первое подошедшее правило решает: сначала метод, затем система, затем проект. Неузнанной системе достаются только общие правила.

Внутри уровня правила идут по `priority`, меньшее число раньше. При равном приоритете раньше то, что создано раньше.

> Порядок в файле действует только внутри одной загрузки. Если два правила одного уровня могут подойти к одному ответу, ставьте `priority`. Это надёжно.

## Примеры из жизни

Все системы ниже выдуманы, но такие ответы встречаются каждый день.

### HTTP 200, а внутри отказ

Система отвечает HTTP 200 всегда. Отказ видно только по полю.

```json part
{ "status": "error", "message": "Limit exceeded" }
```

Без правила это успех: признаков нет. С правилом шаг красный, а причина «Limit exceeded».

```yaml full
version: 1
project: acme
systems:
  - key: limits
    name: Лимиты
    hosts:
      - limits.pay.example
    outcomes:
      - when:
          http: 200
          fields:
            - { path: status, equals: error }
        outcome: error
        text: '{message}'
        action: Передать текст партнёру
```

### HTTP 200, поле error есть всегда

Система пишет `error` в каждом ответе, даже в успешном.

```json part
{ "status": "OK", "error": { "code": 0, "message": "none" } }
```

Без правила это ошибка: поле `error` непустое. С правилом успех.

```yaml full
version: 1
project: acme
systems:
  - key: cards
    name: Карточный сервис
    hosts:
      - cards.pay.example
    outcomes:
      - when:
          http: 200
          fields:
            - { path: status, equals: OK }
        outcome: success
```

### HTTP 422 у одного метода это норма

Метод проверки отвечает 422 с `status = OK`, когда проверка прошла. У остальных методов 422 это ошибка.

```yaml full
version: 1
project: acme
systems:
  - key: check
    name: Сервис проверок
    hosts:
      - check.pay.example
    methods:
      - { http: POST, path: /api/check, name: Проверка реквизитов }
      - { http: POST, path: /api/pay, name: Оплата }
    outcomes:
      - method: { http: POST, path: /api/check }
        when:
          http: 422
          fields:
            - { path: status, equals: OK }
        outcome: success
```

Уровень самый узкий: правило лежит на методе, поэтому `/api/pay` по-прежнему красный на 422.

### HTTP 404 это ответ, а не сбой

Поиск клиента отвечает 404, если клиента нет. Это штатно.

```yaml full
version: 1
project: acme
systems:
  - key: crm
    name: Клиентская база
    hosts:
      - crm.pay.example
    methods:
      - { http: GET, path: '/customers/{userId}', name: Поиск клиента }
    outcomes:
      - method: { http: GET, path: '/customers/{userId}' }
        when: { http: 404 }
        outcome: ignore
```

Шаг не красный, в панели шага «по справочнику не ошибка». В подробностях остаётся HTTP 404.

### Ещё в обработке

Система приняла платёж и обрабатывает его.

```json part
{ "state": "PROCESSING" }
```

```yaml full
version: 1
project: acme
systems:
  - key: pay
    name: Платёжный шлюз
    hosts:
      - gateway.pay.example:8443
    methods:
      - { http: POST, path: /api/charge, name: Списание }
    outcomes:
      - method: { http: POST, path: /api/charge }
        when:
          http: 202
          fields:
            - { path: state, oneOf: [NEW, PROCESSING] }
        outcome: pending
        text: 'Платёж в обработке: {state}'
```

Шаг нейтральный с часами, запрос не ошибочный.

### Код лежит в своём поле

Код отказа в поле `resultCode`. Общие признаки его не знают, поэтому без правила это успех, а правило ошибки его не увидит.

```json part
{ "resultCode": "51" }
```

На каждый код по правилу, текст постоянный:

```yaml full
version: 1
project: acme
systems:
  - key: acquiring
    name: Эквайринг
    hosts:
      - acq.pay.example
    outcomes:
      - when:
          http: 200
          fields:
            - { path: resultCode, equals: '51' }
        outcome: error
        text: Недостаточно средств
        action: Предложите клиенту другую карту
      - when:
          http: 200
          fields:
            - { path: resultCode, equals: '54' }
        outcome: error
        text: Истёк срок действия карты
```

### SOAP и XML

В ответе `<ns2:response_code>0</ns2:response_code>`. Для XML путь это имя элемента.

```yaml full
version: 1
project: acme
systems:
  - key: core
    name: Платёжное ядро
    hosts:
      - core.pay.example:8443
    outcomes:
      - when:
          http: 200
          fields:
            - { path: response_code, equals: '0' }
        outcome: success
```

### Смотрим на тело запроса

Возврат отвечает 409, если он уже был сделан. Это норма только для операции `refund`.

```yaml full
version: 1
project: acme
systems:
  - key: pay
    name: Платёжный шлюз
    hosts:
      - gateway.pay.example:8443
    outcomes:
      - when:
          http: 409
          fields:
            - { in: request, path: operation, equals: refund }
        outcome: ignore
        text: Возврат уже был сделан
```

### Два правила пересекаются

Система отвечает HTTP 200, а поле `status` бывает `OK`, `error` и `partial`. Нужно: `partial` считать успехом, а любой другой ответ с полем `message` считать ошибкой.

```yaml full
version: 1
project: acme
systems:
  - key: batch
    name: Пакетная обработка
    hosts:
      - batch.pay.example
    outcomes:
      - priority: 10
        when:
          http: 200
          fields:
            - { path: status, oneOf: [OK, partial] }
        outcome: success
      - priority: 20
        when:
          http: 200
          fields:
            - { path: message, exists: true }
        outcome: error
        text: '{message}'
```

Ответ `{"status":"partial","message":"2 из 3"}` подходит к обоим правилам. Решает меньший `priority`, поэтому это успех.

### Правило на весь проект

Шлюз перед всеми системами отвечает 504 и пишет в тело `"source": "gateway"`. Правило нужно всем, в том числе неузнанным системам. Условие на поле сужает его: иначе этот текст получат все ответы 504 в проекте, даже если их отдала сама система.

```yaml full
version: 1
project: acme
general:
  outcomes:
    - when:
        http: 504
        fields:
          - { path: source, equals: gateway }
      outcome: error
      text: Система не ответила вовремя
      action: Повторить запрос через минуту
```

## Ловушки

- **`http: 200` и `success` без поля.** Никогда. Такое правило снимет все ошибки в теле.
- **Правило на весь проект только с `http`.** Один текст получат все такие ответы проекта. Добавьте условие на поле. У правил ошибок то же самое: в `general` одного `http` мало, нужны `text` или `code`.
- **`status = OK` без `http`.** Подойдёт и к HTTP 500. Пишите статус и поле вместе.
- **`exists: false`.** Подходит к телу, которое не разобралось: обрезанному, HTML, простому тексту. Лучше пишите `http` и `exists: true` на поле успеха.
- **`equals: 00` без кавычек.** YAML прочитает число 0, а ответ `"00"` с ним не совпадёт. Пишите как в ответе: `equals: '00'`.
- **Поле с личными данными.** `phone`, `pan`, `password` и другие поля, которые маска скрывает, нельзя сравнивать и подставлять. Можно только `exists`.
- **Выводить правило из словаря статусов.** Опрос, который вернул статус «отказ», сам прошёл успешно. Статус операции не должен делать шаг красным.
- **Угадывать.** Нет прямой фразы в документе или примера ответа: правила нет, вопрос в список. Неверное правило красит хорошие запросы в красный или прячет настоящие ошибки.

## Правило оказалось неверным

Удалить правило файлом нельзя. Повторите его с теми же условиями и `hidden: true`. Если поменять условия, это будет новая запись, а старая продолжит работать.
