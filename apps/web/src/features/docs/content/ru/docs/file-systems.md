# Системы

Система: то, с чем работает проект. Сам проект, платёжный шлюз, база данных. Каждая система описана одной записью в списке `systems`, и внутри неё лежат её методы и правила.

## Пример

```yaml full
version: 1
project: acme
systems:
  # Сам проект
  - key: acme
    kind: project
    name: Acme Pay

  # Внешний сервис
  - key: pay
    name: Платёжный шлюз
    hosts:
      - gateway.pay.example:8443
    description: 'REST JSON. Успех: HTTP 200 и status = OK'

  # База данных
  - key: main-db
    type: database
    name: Основная база
    hosts:
      - db.pay.example:5432
```

## Поля

| Поле | Обязательно | Что писать | Где видно |
|---|---|---|---|
| `key` | да | Постоянный ключ: строчная латиница, цифры, дефис, до 32 символов | Адрес раздела справочника: `/acme/catalog/systems/pay`. Сам ключ на страницах запроса не виден |
| `kind` | нет | `project` или `external`. По умолчанию `external` | Источник ошибки в блоке «Итог» |
| `type` | нет | `service`, `database` или `queue`. По умолчанию `service` | Вкладки в справочнике: у базы и шины нет «Методов» |
| `name` | да | Название для людей, до 80 символов | Схема, список запросов, причины ошибки, блок «Итог» |
| `hosts` | нет | Шаблоны хостов, до 50 | По ним узнаётся система. Ещё они видны в разделе системы в справочнике |
| `description` | нет | Как система отвечает, до 500 символов | Только в разделе системы в справочнике |
| `hidden` | нет | `true`: система скрыта | Система и всё внутри неё перестают действовать |
| `methods` | нет | Список методов | «Методы» |
| `errors` | нет | Список правил ошибок | «Ошибки» |
| `outcomes` | нет | Список правил итога | «Правила итога» |

## Ключ

Ключ выбирают один раз и навсегда. Запись находится по нему.

Поменяли `key` в тексте: это новая система, а старая осталась. Если у системы есть хосты, проверка откажет: `хост уже у системы «Платёжный шлюз»`.

Название `name` меняйте сколько угодно.

## Два вида: kind

### Система самого проекта

`kind: project`. Это ваш проект, который пишет логи. Её ещё называют системой-автором, это слово встретится в сообщениях проверки.

- Она одна на проект.
- Её `key` равен идентификатору проекта: у проекта `acme` это `acme`.
- `kind: project` обязателен. Запись с ключом `acme` без него проверка не примет.
- Она всегда `service`.
- Скрыть её нельзя.

Её методы описывают то, что проект принимает: входы и колбэки. К ней же относятся ошибки из записей приложения.

Создавать её не обязательно: Threadline заводит её сам с названием проекта. Пишите её, только когда есть что добавить.

### Внешняя система

`kind: external` или поле не пишут. Это всё, что проект вызывает сам: шлюзы, банки, партнёры.

Отличить просто. Сваггер описывает то, что вызывают у вас: это система проекта. То, что вызываете вы: внешняя система.

### Неизвестно

В файл не пишется. Так Threadline показывает всё, что не узнал: шаг подписан хостом и путём, а строка попадает в раздел «Неизвестное» справочника.

## Три типа: type

| Значение | Что это | Что можно внутри |
|---|---|---|
| `service` | HTTP, SOAP, JSON-RPC. Значение по умолчанию | Методы, ошибки, правила итога |
| `database` | База данных | Только ошибки, без условия `http` |
| `queue` | Шина сообщений | Методов нет, правила итога не работают |

**База данных.** Шаг базы появляется, только если формат логов проекта умеет находить такие записи в логах. Система находится по хосту, а без хоста берётся единственная база проекта. Если баз две, а хоста в записи нет, система неизвестна.

Правила ошибок базы обычно ищут подстроку:

```yaml part
errors:
  - { text: deadlock detected, title: Взаимная блокировка в базе, action: Повторить запрос }
```

Правило итога у базы не сработает: у записи базы нет ответа. Условие `http` в правиле ошибки базы тоже не сработает: у записи нет HTTP-статуса. Файл применится, а проверка предупредит о каждом таком месте.

**Шина сообщений.** Запись можно завести, но отдельных шагов шины Threadline в логах пока не находит. Такая система видна в справочнике, а на странице запроса появится, только если HTTP-вызов идёт на её хост. Проверка об этом предупредит.

## Хосты

Шаблон хоста говорит: вызовы на этот адрес идут в эту систему.

| Шаблон | Подходит | Не подходит |
|---|---|---|
| `gateway.pay.example` | `gateway.pay.example` на любом порту | `api.gateway.pay.example` |
| `gateway.pay.example:8443` | `gateway.pay.example:8443` | `gateway.pay.example:9000` |
| `gateway.pay.example:443` | `https://gateway.pay.example/` без порта в адресе | `http://gateway.pay.example/` |
| `'*.gateway.pay.example'` | `eu.gateway.pay.example`, `a.b.gateway.pay.example` | сам `gateway.pay.example` |
| `192.0.2.10:8443` | этот IP и этот порт | этот IP с другим портом |
| `'[2001:db8::1]:8443'` | этот IPv6 и этот порт | этот IPv6 с другим портом |

Как писать:

- Только хост и порт. Без `https://` и без пути.
- Регистр не важен.
- Шаблон со звёздочкой только в начале, и в нём должна быть точка в домене: `'*.pay.example'` можно, `'*.example'` нельзя. Берите его в кавычки.
- Один шаблон принадлежит одной системе. Повтор даёт ошибку.

Если подходят несколько шаблонов, выигрывает самый точный: сначала с портом, затем точный хост без порта, затем самый длинный `*.домен`.

Настоящие внутренние адреса в `hosts` допустимы: это единственное место, где они нужны. Адресов с логином и паролем быть не должно.

## Система без хостов

Хосты необязательны. Без них система узнаётся по методу: HTTP-метод, путь и действие должны совпасть с методами только этой системы.

Это работает, но ненадёжно. Появится такой же путь у второй системы, и обе станут неизвестными. Указывайте хост, если он есть в документации.

## Скрыть систему

Поставьте `hidden: true`. Система, её методы и правила перестанут действовать, шаги снова будут подписаны хостами. Запись видна в фильтре «Скрытые» в справочнике и в файле.

Чтобы вернуть, уберите `hidden: true`.
