# Ошибки

Правило ошибки переводит код или текст из лога на человеческий язык. Было `error 12: Insufficient funds on account`. Стало «Недостаточно средств» и подсказка, что делать.

## Главное: правило только называет ошибку

Правило ошибки не решает, ошибка это или нет. Оно называет то, что Threadline уже считает ошибкой.

Правило сработает, если есть один из признаков:

- ответ с HTTP 400 и выше;
- в теле ответа есть признак ошибки, список ниже;
- запись приложения с уровнем WARNING и выше.

Хороший ответ правило ошибки красным не сделает. Если ответ ошибочный, а признака нет, нужно правило итога.

## Пример

```yaml full
version: 1
project: acme
systems:
  - key: acme
    kind: project
    name: Acme Pay
    errors:
      - text: duplicated user
        title: Такой клиент уже есть
        action: Найти клиента по номеру договора
  - key: pay
    name: Платёжный шлюз
    hosts:
      - gateway.pay.example:8443
    methods:
      - { http: POST, path: /api/charge, name: Списание }
      - { http: POST, path: /api/refund, name: Возврат }
    errors:
      # Правило всей системы
      - code: '12'
        title: Недостаточно средств
        action: Предложите клиенту другую карту
        partnerCode: '150'
      # Правило одного метода: сильнее правила системы
      - method: { http: POST, path: /api/refund }
        code: '12'
        title: На счёте партнёра нет денег для возврата
        action: Передать в расчётный отдел
      # HTTP 404 и нужный код вместе
      - http: 404
        code: ERR-CARD
        title: Карта не найдена
      # Это не ошибка
      - code: '00'
        title: Операция одобрена
        severity: ok
general:
  errors:
    # Одного статуса в общем правиле мало: нужны ещё text или code
    - http: 504
      text: gateway timeout
      title: Система не ответила вовремя
      action: Повторить запрос через минуту
```

## Поля

| Поле | Обязательно | Что писать | Где видно |
|---|---|---|---|
| `http` | условие | HTTP-статус ответа, целое от 100 до 599 | Условие. Исходный статус виден в «Итоге» |
| `code` | условие | Код ошибки, до 64 символов, лучше в кавычках | Условие. Исходный код виден в «Итоге» |
| `text` | условие | Подстрока текста ошибки, от 3 до 200 символов | Условие |
| `title` | да | Понятный текст, до 200 символов | Причина ошибки, схема, блок «Итог», строка списка |
| `action` | нет | Что делать, до 500 символов | Строка «Что делать» в панели шага |
| `severity` | нет | `error` или `ok`. По умолчанию `error` | `ok`: шаг не красный, пометка «по справочнику не ошибка» |
| `partnerCode` | нет | Код, который партнёр получит от проекта, в кавычках | «партнёр получит код 150 по реестру» в блоке «Итог» |
| `method` | нет | Ссылка на метод этой системы. Только в `systems` | Делает правило правилом метода |
| `hidden` | нет | `true`: правило не действует | |

Нужно хотя бы одно условие: `http`, `code` или `text`. Подходит правило, у которого совпали все условия.

В `general` одного `http` мало: такой текст получат все ошибки с этим статусом во всём проекте. Добавьте `text` или `code`. Файл без них применится, а проверка предупредит. Форма новое правило только со статусом не сохранит. Правило только с `code` допустимо.

Текст `title` пишется как есть, подстановок в нём нет. Нужен текст из тела ответа: это делает правило итога.

## Условия

**Код `code`.** Сравнивается с кодом из ответа. Коды из одних цифр сравниваются как числа: `'00'`, `'0'` и `0` это один код. Остальные как текст без пробелов по краям.

**Подстрока `text`.** Ищется в тексте ошибки. Регистр, лишние пробелы и переводы строк не важны: `error: duplicate key` найдётся и в `ERROR:  duplicate key`, и в тексте на двух строках. Берите различимый кусок: `PRC-ERR-0027`, `deadlock detected`. У ответа без признака в теле Threadline смотрит только первые 200 символов тела.

**Статус `http`.** Сравнивается с настоящим статусом ответа, в том числе ниже 400: `http: 200` и `code: '12'` подойдут к ответу HTTP 200 с кодом 12. У записи приложения статуса нет, поэтому правило с `http` к ней не подойдёт.

## Откуда берётся код

Threadline читает код только из определённых мест.

| Что в теле ответа | Считается ошибкой, если | Код берётся из | Текст берётся из |
|---|---|---|---|
| `error` | Поле непустое | `error.code`, `errorCode`, `error_code` | `error.message` и похожие поля |
| `result` | Равно `error` | `code`, `error_code` | `message` и похожие поля |
| `success` | Равно `false` | кода нет | `message` и похожие поля |
| `res` вместе с `error` | `res` не равно 0 | `res` | `message` и похожие поля |
| `result_code` | Не равно `GOOD` | `result_code` | `message` и похожие поля |
| `transStatus` | Равно `N` | `N` | `transStatusReason` |
| `resultInfo.code` | Не равно 0 | `resultInfo.code` | `resultInfo.message` и похожие поля |
| `statuses.item`, элемент с `type: card` | `actionCode` не равно `000` | `actionCode` | `actionDescription` |
| XML, элемент `response_code` | Не равно 0 | `response_code` | `error_description` |

Похожие поля: `message`, `description`, `errorMessage`, `error_message`, `error_description`, `title`.

У записи приложения код берётся из контекста: `code`, `error_code` или `error.code`. Текст: её сообщение.

Если код лежит в другом поле, например `resultCode`, правило ошибки его не увидит. Тут нужно правило итога.

## Уровни: метод, система, проект

Правило лежит на одном из трёх уровней.

| Уровень | Где лежит | К чему относится |
|---|---|---|
| Метод | `systems[].errors[]` с полем `method` | Только этот метод |
| Система | `systems[].errors[]` без `method` | Все методы системы |
| Проект | `general.errors[]` | Все системы, в том числе неузнанные |

Ссылка `method` должна совпасть с методом этой системы по `http`, `path` и `rpc`. Имена подстановок могут отличаться. Метод должен быть в этом файле или уже в проекте.

```yaml part
errors:
  - method: { http: POST, path: /, rpc: p2p.transfer }
    code: '-200'
    title: Карта получателя не найдена
```

## Порядок

Первое подошедшее правило решает.

1. Правила метода этого шага.
2. Правила его системы.
3. Общие правила проекта.
4. Не нашлось: источник «неизвестно», показаны исходные код и текст. Если система узнана, ошибка попадает в «Неизвестное» справочника.

Внутри одного уровня выигрывает правило, у которого больше условий. При равенстве правило с кодом, затем правило с текстом, затем созданное раньше.

У неузнанной системы проверяются только общие правила.

Записи приложения относятся к системе проекта и к методу входа этого запроса.

## Не ошибка: severity ok

Иногда признак срабатывает зря. Например, система всегда отдаёт `error: { code: "00", message: "Approved" }`. Без правила такой ответ красный.

```yaml part
errors:
  - { code: '00', title: Операция одобрена, severity: ok }
```

Шаг перестанет быть красным, запрос без других причин станет успешным. Текст останется виден в панели шага с пометкой «по справочнику не ошибка».

> `severity: ok` может спрятать настоящую ошибку. Пишите его только по прямой фразе в документе.

Если условие не про код, а про HTTP или другое поле, нужно правило итога с `outcome: ignore`.

## Что писать в текстах

- `title` отвечает на вопрос «что случилось»: «Недостаточно средств», а не «Ошибка 12».
- `action` отвечает на вопрос «что делать» для второй линии: «Предложите клиенту другую карту». Только то, что написано в документе. Не знаете: не пишите.
- `partnerCode` только по таблице соответствия кодов. Не придумывайте.
- `general` только если так решил владелец проекта: такое правило действует на все системы. Пишите его с `text` или `code`.

Настоящих значений в текстах быть не должно. Номер карты или телефон проверка отклонит.

## Правило оказалось неверным

Удалить правило файлом нельзя. Повторите его с теми же условиями и `hidden: true`. Новое условие даёт новую запись, а старая продолжает работать.

```yaml part
errors:
  - { code: '12', title: Недостаточно средств, hidden: true }
```
