# Id и операции

Операция: дело из нескольких запросов, например платёж: создание, опрос статуса, колбэк. Запросы одной операции связывает её id. Чтобы Threadline увидел эту связь, файл говорит, где лежит id и какого он типа.

На странице запроса появляется кнопка «Открыть операцию». Страница операции собирает все запросы этого дела и показывает итог.

## Пример

```yaml full
version: 1
project: acme
idTypes:
  - key: user
    kind: entity
    name: Клиент
  - key: transfer
    kind: operation
    name: Перевод
    statuses:
      - { value: created, name: Создан, outcome: pending }
      - { value: processing, name: В обработке, outcome: pending }
      - { value: completed, name: Выполнен, outcome: success }
      - { value: failed, name: Отказ, outcome: failure }
systems:
  - key: acme
    kind: project
    name: Acme Pay
    methods:
      # Id в пути: тип найден по имени подстановки
      - http: GET
        path: /v1/users/{userId}/transfers/{transferId}
        name: Статус перевода
        kind: status
        op: transfer
        status: { in: response, path: data.state }
      # Колбэк: id и статус в теле входящего запроса
      - http: POST
        path: /internal/callbacks/transfer
        name: Колбэк перевода
        kind: callback
        op: transfer
        fields:
          - { in: request, path: remote_transfer_id, type: transfer }
        status:
          in: request
          path: state
          map: { complete: completed, error: failed }
  - key: pay
    name: Платёжный шлюз
    hosts:
      - gateway.pay.example:8443
    methods:
      # Создание: id выдал ответ
      - http: POST
        path: /api/transfer
        name: Отправка перевода
        kind: start
        op: transfer
        fields:
          - { in: response, path: data.transfer_id, type: transfer }
```

## Типы id

Тип id говорит, что это за идентификатор. Все типы лежат в списке `idTypes`.

| Поле | Обязательно | Что писать |
|---|---|---|
| `key` | да | Ключ: латиница в нижнем регистре, цифры и `_`, с буквы, до 32 символов. На экране не виден, на него ссылаются методы |
| `kind` | да | `entity` или `operation` |
| `name` | да | Название, до 80 символов. Видно на кнопке операции и в блоке «Итог» |
| `statuses` | нет | Словарь статусов. Только у `operation`, до 30 значений |
| `hidden` | нет | `true`: тип скрыт. Тип, на который ссылаются методы, скрыть нельзя |

**Операция, `kind: operation`.** Платёж, перевод, заявка, рассрочка. От такого id появляется кнопка «Открыть операцию».

**Сущность, `kind: entity`.** Клиент, карта, счёт. Тип виден в разделе «Идентификаторы» справочника. На страницах запроса и операции id сущности сейчас не показан и кнопки не даёт. Файл применится, а проверка об этом предупредит. Заводить такой тип необязательно: подстановка без типа ничего не ломает.

Правила выбора типа:

- Один и тот же номер в разных системах: один тип.
- Свой номер у внешней системы: свой тип. Например, `transfer` и `partner_transfer`.
- Типы, которые уже есть в проекте, повторять в файле не нужно. Повторили: тип заменится целиком, вместе со словарём.

## Где лежит id

### В пути

Тип находится по имени подстановки. Имя приводится к ключу типа:

| Имя подстановки | Ключ типа |
|---|---|
| `{transfer}` | `transfer` |
| `{transferId}` | `transfer` |
| `{transfer_id}` | `transfer` |
| `{qrPaymentId}` | `qr_payment` |
| `{qr-payment}` | `qr_payment` |
| `{card2}` | `card` |
| `{cardId2}` | `card` |
| `{id}` | `id` |

Подстановка `{id}` получит тип, только если у вас есть тип с ключом `id`. Если документ говорит, чей это id, переименуйте: `{id}` в `{transferId}`. Метод от этого не изменится.

Подстановка без подходящего типа не мешает: метод узнаётся как обычно, но id у него нет.

Вторая подстановка того же типа пишется с цифрой: `{card2}` или `{cardId2}`.

### Вне пути: поле fields

Если id лежит в строке запроса или в теле, укажите его в `fields`.

| Поле | Что писать |
|---|---|
| `in` | `query`: строка запроса. `request`: тело запроса. `response`: тело ответа |
| `path` | Путь поля. У `query` имя параметра |
| `type` | Ключ типа. Тип должен быть в файле или уже в проекте |

```yaml part
fields:
  - { in: query, path: ref, type: transfer }
  - { in: request, path: request_id, type: transfer }
  - { in: response, path: data.transfer_id, type: transfer }
```

У одного метода до 10 таких полей. Правила пути те же, что у правил итога: в JSON имена через точку, без массивов, в XML имя элемента.

Поля со скрытыми данными указывать нельзя: `password`, `pan`, `phone`, `accountId` и другие. Проверка откажет. Поле, которое Администратор сам добавил к виду маски, указывать можно: значение будет показано маской.

Если значение скрыто маской, кнопка операции видна, но недоступна: подсказка «id скрыт маскированием». Threadline не ищет операцию по маске.

## Статус операции

### Словарь

У типа операции можно завести словарь статусов, по порядку жизни операции.

| Поле | Что писать |
|---|---|
| `value` | Значение как в ответе, до 64 символов. Цифры в кавычках: `value: '2'` |
| `name` | Название для людей, до 80 символов |
| `outcome` | `pending`: ещё идёт. `success`: успех. `failure`: отказ |

Значения сравниваются без учёта регистра. Значение, которого нет в словаре, показывается как есть, без названия и итога. Смысл значения не описан в документе: не вносите его, оно просто покажется как есть.

### Поле статуса у метода

Поле `status` говорит, где у этого метода лежит статус. Оно бывает только у метода с `op`.

| Поле | Что писать |
|---|---|
| `in` | `request` или `response` |
| `path` | Путь поля |
| `map` | Перевод значений из лога в значения словаря, без учёта регистра |

`map` нужен, когда система пишет статус своими словами:

```yaml part
status:
  in: request
  path: state
  map: { complete: completed, error: failed }
```

Значение в правой части обязано быть в словаре типа.

### Что статус не делает

Статус не меняет цвет шага и статус запроса. Опрос, который вернул «Отказ», сам прошёл успешно: шаг зелёный, а итог операции «Отказ».

Чтобы шаг стал красным, нужно правило итога.

Статус у ответа на вход читается, только если такая запись есть в логе. Нет записи: нет и статуса.

## Что поля op и kind дают на экране

| Что в файле | Что на экране |
|---|---|
| Id типа `operation` в пути или в `fields` | Кнопка «Открыть операцию · Перевод …4f2a» в шапке запроса: название типа и последние 4 символа id |
| `kind` и `op` у метода | В блоке «Итог»: «Статус · Перевод · Выполнен» |
| `status` и словарь | На схеме «опрос ×5 · Выполнен». На странице операции «Ход операции» |
| `outcome: success` или `failure` в словаре | Итог на странице операции. Берётся последний по времени финальный статус, который пришёл не из колбэка |
| `kind: callback` | На странице операции статус с пометкой «заявлено в колбэке» |
| `kind: start` и id в ответе | На схеме «id выдан …4f2a» |

## Частые вопросы

**Кнопки «Открыть операцию» нет.** В запросе нет id вида `operation`. Проверьте, что имя подстановки или `fields` указывают на тип с `kind: operation`, а метод узнан.

**Статуса нет.** Проверьте `in`, `path` и что метод с `op`. Если тело ответа не разобралось или поля в нём нет, статуса тоже нет: остальное на шаге работает.

**Запросы одной операции не связались.** В них должно быть одно и то же значение одного и того же типа. Разные номера у разных систем: заведите метод, где встречаются оба. Например, ответ, где лежит и ваш номер, и номер партнёра.
