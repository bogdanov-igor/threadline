# Как превратить документацию и сваггеры в справочник

Порядок работы для аналитика или разработчика, который переносит документацию систем в справочник. Поля файла описаны
в [README.md](./README.md) и [catalog.schema.json](./catalog.schema.json), здесь — откуда их брать и как проверять.
Команды запускаются из корня репозитория на Node 24.

То же самое подробно и с примерами лежит в документации сервиса, группа «Файл проекта». Страницы открываются
по адресу `/docs/<страница>`, текст лежит в `apps/web/src/features/docs/content/ru/docs/<страница>.md`:

| Страница | О чём |
|---|---|
| `file-start` | что такое файл, маленький рабочий пример |
| `file-how` | скачать, править, проверить, применить, конфликт, команда, кавычки YAML |
| `file-settings` | раздел `settings` |
| `file-systems` | системы и хосты |
| `file-methods` | как находится метод, шаблоны пути, `rpc`, виды |
| `file-errors` | правила ошибок |
| `file-outcomes` | правила итога и примеры |
| `file-ids` | типы id, операции, статусы |
| `file-masks` | раздел `masking` |
| `file-from-swagger` | порядок работы и проверка готового файла |
| `file-errors-reference` | все сообщения проверки и что с ними делать |
| `file-all-fields` | полная таблица полей |

Примеры этих страниц и таблицу полей сверяет тест `apps/server/test/docs-file-examples.test.ts`.

**Главное правило: не угадывать.** Чего в документации нет или что в ней противоречит, в файл не идёт, а идёт в список
вопросов (раздел 8). Неточное название только выглядит плохо, а неверное правило итога красит хорошие запросы в красный
или прячет настоящие ошибки.

## 1. Что собрать и где хранить

| Что | В каком виде |
|---|---|
| Описание API | OpenAPI или Swagger (YAML, JSON), коллекция Postman, WSDL |
| JSON-RPC и SOAP без сваггера | адрес, список действий, пример запроса и ответа |
| Ошибки | таблица: код, HTTP-статус, текст, что делать (Markdown, Excel, CSV, PDF, выгрузка wiki) |
| Статусы операций | enum или таблица: значение и его смысл |
| Критерий успеха | фраза «что считается успехом», примеры успешного и ошибочного ответа |
| Хосты | адреса системы по средам |

Исходники кладите в `~/threadline-sources/<проект>/<система>/`, файлы справочника и списки вопросов — в
`~/threadline-sources/<проект>/portions/`. Не в репозиторий: каталог `config` и код входят в образ Docker.

Настоящих данных клиентов в исходниках быть не должно: ни логов, ни тел ответов, ни номеров карт, имён, телефонов, токенов.
Нашли такое — не переносите и не копируйте эти данные и сообщите владельцу проекта.

## 2. Откуда какое поле

| Источник | Поле файла | Как |
|---|---|---|
| `info.title` | `systems[].key`, `name` | `key`: строчная латиница, цифры, дефис; один на систему навсегда |
| `servers[].url` | `hosts` | только хост и порт: `https://api.partner.example:8443/gw/v2` → `api.partner.example:8443`. Порта нет — хост без порта. `localhost`, `example.com`, шаблоны с `{env}` не брать |
| `servers[].url`, путь | начало `path` | в `path` полный путь, как в логе: `/gw/v2` + `/payments` = `/gw/v2/payments` |
| `paths` и HTTP-метод | `methods[].http`, `path` | своя запись на каждую пару. `'*'` — только если HTTP-метод не назван |
| `summary` | `name` | по-русски, до 80 символов. Нет — первая фраза `description`, затем `operationId`, затем путь и вопрос в список. `deprecated` — метод остаётся, в названии «(устарел)» |
| `tags[0]`, `description` | `domain`, `description` | до 40 и до 500 символов, без примеров |
| таблица ошибок, `responses` | `errors[]` | раздел 4 |
| фраза о том, что считать успехом | `outcomes[]`, `systems[].description` | раздел 5 |
| enum статуса | `idTypes[].statuses`, `methods[].status` | раздел 6 |

Не переносите `example`, `examples`, `default`, `securitySchemes`, заголовки.

Шаблон пути: подстановка занимает сегмент целиком; без `?` и без `/` в конце; регистр значим. `/files/{name}.json` и
`/users/{id}:activate` так не записать — в список вопросов.

## 3. Три источника

- **Проект** — система-автор: `kind: project`, `key` равен id проекта (`pay`), одна на проект. Её методы — то, что проект
  принимает: входы и колбэки. К ней же относятся ошибки из записей приложения.
- **Внешняя система** — всё, что проект вызывает сам. `kind` не пишется. База и шина — `type: database` и `type: queue`, без методов.
  Отдельных шагов шины Threadline в логах не находит: такая система видна в справочнике и на HTTP-вызове на её хост. Правила итога у базы и шины не действуют: ответа нет. Условие `http` в ошибке базы тоже: статуса нет. Проверка предупредит о каждом таком месте и о самой шине.
- **Неизвестно** — в файл не пишется. Так Threadline показывает всё, чего нет в справочнике (раздел 10).

Как отличить: сваггер описывает то, что вызывают у нас, — проект; то, что вызываем мы, — внешняя система. Неясно — вопрос.

**JSON-RPC и SOAP: путей нет, действие в теле.** Каждое действие — своя запись: `http: POST` (не назван — `'*'`), `path` —
адрес (`/` для корня), `rpc` — поле `method` у JSON-RPC или первый элемент `Body` без префикса у SOAP.

- Запись без `rpc` на этот путь не заводите: на неё упадут все незнакомые действия и получат чужое название.
- Действие читается, только если в теле JSON есть поле `jsonrpc`. Тело с `method`, но без `jsonrpc` — вопрос в список.
- Хост указывайте: без него система узнаётся, только если это действие есть у неё одной.
- Действие читается только на вызовах. Для входа в проект оно не читается: метод системы-автора с `rpc` на входе не сработает, проверка предупредит. Проект сам принимает JSON-RPC или SOAP на одном адресе — один метод без `rpc`, вопрос в список.

## 4. Ошибки

Правило ошибки только называет уже найденную ошибку: оно работает, если ответ HTTP 400 и выше, в теле есть общий признак
(раздел 5) или это запись приложения уровня WARNING и выше. Хороший ответ красным оно не сделает, а `severity: ok` может спрятать ошибку.

- Порядок: **правило метода → правило системы → общее правило проекта**, первое подошедшее решает. Внутри уровня — больше условий,
  затем с кодом, затем с текстом, затем созданное раньше. Не нашлось — источник «неизвестно».
- `code` — код из таблицы, в кавычках. `'00'` и `'0'` — один код. Код читается только из полей общего признака (`error.code`, `res`,
  `result_code`, `response_code` и других), у записи приложения — из контекста (`code`, `error_code`, `error.code`), и условие
  `http` к ней не подходит. Код в другом поле, например `resultCode`, — только правилом итога.
- `text` — различимая подстрока от 3 символов, когда кода нет. `title` — текст по-русски, не шаблон. `action` — «что делать», только из документа.
- `partnerCode` — только по таблице соответствия. `general` — только если так решил владелец проекта: правило действует на все системы. Одного `http` там мало: нужны ещё `text` или `code`, иначе проверка предупредит.

## 5. Итог ответа

Без правила ответ — ошибка, если HTTP 400 и выше или в теле **общий признак**: непустое `error`, `result = error`,
`success = false`, `res ≠ 0` вместе с `error`, `result_code` не `GOOD`, `transStatus = N`, `resultInfo.code ≠ 0`,
`actionCode ≠ 000` у `type = card` в `statuses.item`, в XML `response_code ≠ 0` или `actionCode ≠ 000` у карты. Иначе — успех.

1. Найдите прямую фразу или пример ответа: что успех, что ошибка. Нет — правила нет, вопрос в список.
2. Примените к этому ответу признаки выше. Результат совпал с документом — правило не нужно.
3. Не совпал — пишите правило. Условия узкие: HTTP-статус и поле вместе.
4. Уровень самый узкий: сказано о методе — `method`, сказано о всех методах системы — система.
5. Итог: `success` — операция удалась, `error` — нет, `pending` — ещё идёт, `ignore` — ответ отрицательный, но это норма.

| Ответ | Что сказано в документе | Без правила | Что пишем |
|---|---|---|---|
| 200 `{"status":"OK"}` | OK — успех | успех | ничего |
| 200 `{"status":"OK","error":{"code":0,"message":"none"}}` | OK — успех, `error` есть всегда | ошибка | система: `http: 200`, `status = OK` → `success` |
| 200 `{"status":"error","message":"Limit exceeded"}` | `error` — отказ, текст в `message` | успех | система: `http: 200`, `status = error` → `error`, `text: '{message}'` |
| 200 `{"resultCode":"51"}` | 51 — нет средств | успех | система: `http: 200`, `resultCode = '51'` → `error`, `text: Недостаточно средств` |
| 422 `{"status":"OK"}` у `/check` | для этого метода норма | ошибка | метод: `http: 422`, `status = OK` → `success` |
| 404 у поиска клиента | «не найден» — штатный ответ | ошибка | метод: `http: 404` → `ignore` |
| 200 `{"error":{"code":"00","message":"Approved"}}` | 00 — успех | ошибка | `errors`: `code: '00'`, `severity: ok` |
| 202 `{"state":"PROCESSING"}` | ещё обрабатывается | успех | метод: `http: 202`, `state = PROCESSING` → `pending` |

«Не ошибка» записывается двумя способами. Код уже попадает в общий признак — правило ошибки с `severity: ok`. Условие по HTTP
или другому полю — правило итога с `ignore`. Шаг не красный, текст виден с пометкой «по справочнику не ошибка».

Правила итога проверяются раньше правил ошибок, в том же порядке: **метод → система → общее правило**, внутри уровня по `priority`
(меньше — раньше). Первое подошедшее решает итог. Неузнанной системе достаются только общие правила.

Ловушки:

- `http: 200 → success` без поля — никогда: снимает все ошибки в теле. `status = OK` без `http` подойдёт и к HTTP 500.
- `exists: false` подходит к телу, которое не разобралось: обрезанному, HTML. Пишите `http` и `exists: true` на поле успеха.
- Правила одного уровня пересекаются — ставьте `priority`. Порядок в файле действует только внутри одного импорта.
- Путь поля — через точку по объектам, без массивов; в XML — локальное имя первого такого элемента. Статус в массиве или ответ
  простым текстом правилом не выразить — вопрос в список.
- `equals` сравнивает текст: `'00'` и `0` — разные значения. Пишите в кавычках, как в ответе.
- Правило не проверяется на записях приложения и отправках без ответа. Если запись самого ответа сделана с уровнем WARNING и выше,
  причина по уровню остаётся: правило итога её не снимает.

Правило оказалось неверным — повторите его в файле с теми же условиями и `hidden: true`.

## 6. Id и операции

- `idTypes[]`: `kind: operation` (платёж, перевод) со словарём. Тип `kind: entity` (пользователь, карта, счёт) без статусов заводите, только если он нужен в справочнике.
  Типы из выгрузки можно не повторять. Повторили — тип заменится целиком, со словарём.
- Id в пути определяется по имени подстановки: `{card_id}`, `{cardId}`, `{card}` дают тип `card`. Вторая подстановка того же типа — с цифрой: `{card2}` или `{cardId2}`.
  `{id}` id не покажет: переименуйте, если документ говорит, чей это id. Id вне пути — `fields`: `{ in: query, path: ref, type: card }`, `in` бывает `query`, `request`, `response`.
- На экране работает только вид `operation`: кнопка «Открыть операцию» и страница операции. Id вида `entity` на страницах запроса и операции не показан, проверка об этом предупредит.
- Один и тот же номер в разных системах — один тип. Свой номер внешней системы — свой тип: `transfer` и `payout`.
- `kind` метода: `call` по умолчанию, `start` создаёт операцию, `status` отдаёт её статус, `callback` — входящий колбэк, только
  у проекта. У `start`, `status` и `callback` обязателен `op` — ключ типа вида `operation`.
- Словарь: значения enum по порядку жизни, `value` как в ответе, `name`, `outcome`: `pending`, `success`, `failure`. Смысл значения
  не описан — не вносите: оно покажется как есть, вопрос в список.
- Поле статуса: `status: { in: response, path: data.state }`. Значения в ответе другие — `map` переводит их в значения словаря.
- Статус только подпись и не меняет цвет шага. Правило итога из словаря не выводите: опрос, вернувший «отказ», сам успешен.

## 7. Чего в файле не бывает

Секретов: токенов, паролей, ключей, логинов интеграций, адресов с логином. Настоящих значений: номеров карт и масок, имён, телефонов,
личных номеров, паспортов, счетов, id, сумм, тел ответов; из примеров «Неизвестного» берите только код, имя поля и шаблон пути.

Поля `password`, `access_token`, `pin`, `cvv`, `client_secret`, `Authorization`, номер карты по имени поля и встроенные поля включённых по умолчанию видов маски (`phone`, `accountId`, `card_tokens` и другие) нельзя указывать как id,
статус, `{путь}`, `equals`, `oneOf`, `regex`, можно только `exists`. Импорт ловит значения, которые скрыла бы маска, но имён в тексте не видит:
за них отвечает автор файла. Внутренние адреса сервисов в `hosts` допустимы.

### Раздел `settings`

Файл проекта может нести настройки: название, часовой пояс, срок хранения, профиль формата по имени, среды с условиями и настройку вида. **Порции обходятся без него:** раздела нет, настройки не меняются и права на них не проверяются. Пишите его, только если задача именно в настройках.

- Чего в нём нет: токенов, секретов, `url`, `tokenEnv`, `datasource`, определений хранилищ `backends`, тела профиля `formats`, логотипов, `id` проекта, меток версии и скрытия. Такие поля дают ошибку с путём: они живут в файле настроек и на формах.
- Изменившийся раздел проходит те же проверки, что формы: граница хранилища `formScope`, занятые идентификаторы, лимиты. Совпавший с базой не проверяется и правкой не считается.
- Кто меняет: в сервисе аналитик и администратор, чужой файл отклоняется целиком с путём `settings`. Команда прав не проверяет.
- Среду, которой нет в файле, импорт не убирает: она считается в «Нет в файле», убирают её на форме «Среды». Порядок сред хранится.
- Начальный набор раздел пропускает, остальное применяет, в журнале предупреждение. Начальные настройки даёт только файл настроек.
- **Команда применяет раздел без сверки версии:** у неё нет открытого текста. Поэтому выгружайте файл прямо перед правкой, сначала `--dry-run`: отчёт называет изменённые поля. Записи проекта в базе ещё нет (сервер ни разу не запускался): `export` пишет файл без раздела и предупреждает, `import` с разделом даёт ошибку.

## 8. Документ противоречит себе или молчит

| Случай | Что делать |
|---|---|
| Документы расходятся в пути, HTTP-методе или коде | записи нет |
| У кода два смысла | записи нет. Смысл зависит от метода и это сказано прямо — правила методов |
| Не сказано, что считать успехом; описание и пример ответа расходятся | правил итога нет. Методы и ошибки заводите |
| Значение статуса без смысла | значения в словаре нет |
| Форма не выражается: массив, часть сегмента пути | записи нет |

Остальное из порции загружается. Рядом с порцией ведите `portions/<система>.questions.md`, строка на вопрос: метод или код; что
неясно; файл и раздел; варианты, если видны. Без настоящих значений. Список отдаётся владельцу проекта, ответы идут в новую версию порции.

## 9. Порции и команды

Одна система — один файл до 2 МБ, файл применяется целиком или никак. Плохой файл держит только себя: исправьте его или вынесите
запись в вопросы, остальные идут дальше. Порядок: новые типы id отдельным файлом (`00-types.yaml`), проект, внешние системы.
Адрес базы — `THREADLINE_DATABASE_URL` из окружения или `.env`; `import` без `--dry-run` сразу меняет эту базу.

```bash
mkdir -p ~/threadline-sources/pay/portions
pnpm threadline:catalog schema ~/threadline-sources/catalog.schema.json        # схема этой версии
pnpm threadline:catalog export pay ~/threadline-sources/pay/portions/pay-now.yaml # 1. что уже есть
pnpm threadline:catalog import pay ~/threadline-sources/pay/portions/demo-gw.yaml --dry-run  # 2. проверка без записи
pnpm threadline:catalog import pay ~/threadline-sources/pay/portions/demo-gw.yaml            # 3. загрузка
```

Без доступа к базе форму файла проверяет пустая база в памяти (только в разработке): `THREADLINE_DATABASE_URL=pglite://memory`
перед той же командой `--dry-run`. Типы id и методы, которых нет в файле, там покажутся ошибкой, а раздел `settings` даст ошибку «записи проекта в базе ещё нет», поэтому шаг 2 это не заменяет.

Код выхода: 0 — успех, 1 — ошибка файла, 2 — база недоступна. В списках отчёта первые 200 строк.

| Строка отчёта | Что с ней делать |
|---|---|
| `Ошибки файла (N), ничего не применено` | исправить по пути: `systems.1.methods.3.path` — вторая система, четвёртый метод |
| `Предупреждения (N)` | файл применяется, но эти поля не действуют: убрать или оставить намеренно, что делать, написано в строке. Код выхода не меняют |
| `Добавлено` | сверить с документом |
| `Изменено` (поля в скобках) | проверить каждую: не стирает ли файл нужное |
| `Скрыто` | только то, что скрывали намеренно |
| `Возвращено` | скрытая запись снова без `hidden: true`. Только намеренно |
| `Удалённые записи файл не возвращает` | запись удалили в редакторе. Оставить, значение файла в вопросы |
| `Ручные правки пропущены` | аналитик правил запись. Оставить, значение файла в вопросы |
| `Без изменений`, `Нет в файле` | большое число в порции — норма: импорт не удаляет |

Как ведёт себя импорт:

- **Запись заменяется целиком, пропущенное поле становится пустым.** Запись из выгрузки переносите со всеми полями:
  `{ key: demo-partner, name: Demo Partner }` сотрёт `hosts` и `description`. Записи системы, которых нет в файле, не тронуты.
- Запись ищется по ключу: метод — `http`, путь, `rpc`; ошибка и правило — место и условия. Новое условие даёт новую запись, а старая
  продолжает работать: повторите старую с `hidden: true`. Метод из выгрузки с `http: '*'` и тот же путь с `POST` — две записи:
  оставляйте `'*'`, как в выгрузке.
- Удалить нельзя, только `hidden: true`. Один шаблон хоста — у одной системы. Работающий сервер увидит изменения за 30 секунд.
- Запись, которую правили или создали в редакторе, без `--force` не меняется. `--force` заменяет такие записи значениями файла,
  возвращает скрытые, и записи больше не считаются ручными. Только если так решил владелец проекта, сначала `--dry-run --force`.

В YAML берите в кавычки `'*'`, шаблон хоста `'*.domain'`, `code`, `equals`, `partnerCode`, цифровой `value` статуса, `text: '{message}'`, `op: '!='`, путь с `{}` внутри `{ … }` и всё, где после двоеточия пробел.

**В конце всех порций** выгрузите итог в начальный набор: `pnpm threadline:catalog export pay config/catalog/pay.yaml`. Этот файл входит
в образ и импортируется при подключении к базе, если изменился. Останется старым — новая среда порций не увидит, а при его следующем
изменении старые значения заменят загруженные.

**Разделы `settings` и `masking` удалять не нужно:** начальный набор их пропустит, настройки и маски не изменятся, в журнале будет предупреждение. Поэтому файл не выключит маску в другой среде: новая база получает встроенные маски. Маски меняют на странице «Файл проекта» или командой `import`.

## 10. «Неизвестное»: что ещё не описано

Страница `/pay/catalog/unknown`, сверху самое частое; у сервера — `GET /api/projects/pay/catalog/unknown?kind=method|host|error`, страницы
по 100. Список пополняется, когда ищут в средах с настоящими логами. Пустой список значит только, что встреченное узнано, а не что описано всё.

| Строка | Что значит | Как закрыть |
|---|---|---|
| Метод | вход проекта или метод узнанной системы не описан | `methods[]` этой системы |
| Хост | обмен с хостом без системы; его ошибки отдельно не собираются | `hosts` новой или существующей системы |
| Ошибка | у узнанной системы нет правила | `errors[]` или правило итога |

Строка уходит сама, как только запись её покрывает. Правило итога с условием по полю строку не убирает: новые случаи перестают
копиться, а строку после проверки скройте кнопкой «Скрыть». «Открыть пример» ведёт на запрос: там видно, какой итог дало правило.

Рабочий цикл: загрузить порцию, поискать за тот же период, взять верх «Неизвестного», найти в документации. Нет в документации — вопрос в список.

## 11. Пример файла

Все значения вымышлены, в настоящий справочник не загружайте. Проверка на пустой базе: `Добавлено: 19`, ошибок нет, одно предупреждение о типе `user`.

```yaml
# yaml-language-server: $schema=./catalog.schema.json
version: 1
project: pay
idTypes:
  - { key: user, kind: entity, name: Пользователь }
  - key: partner_payment
    kind: operation
    name: Платёж партнёра
    statuses:
      - { value: CREATED, name: Создан, outcome: pending }
      - { value: PAID, name: Оплачен, outcome: success }
      - { value: DECLINED, name: Отклонён, outcome: failure }
systems:
  - key: pay
    kind: project
    name: Demo Pay
    methods:
      - http: POST
        path: /internal/callbacks/demo-partner
        name: Колбэк Demo Partner
        kind: callback
        op: partner_payment
        fields: [{ in: request, path: payment_ref, type: partner_payment }]
        status: { in: request, path: state, map: { done: PAID, rejected: DECLINED } }
  - key: demo-partner
    name: Demo Partner
    hosts: ['api.demo-partner.example:8443']
    description: 'REST JSON. Успех: HTTP 200 и status = OK, поле error есть всегда. Отказ: HTTP 200, status = error, текст в message'
    methods:
      - http: POST
        path: /gw/v2/payments
        name: Создание платежа
        domain: Платежи
        kind: start
        op: partner_payment
        fields: [{ in: response, path: data.payment_ref, type: partner_payment }]
        status: { in: response, path: data.state }
      - http: GET
        path: /gw/v2/payments/{partner_payment_id}
        name: Статус платежа
        domain: Платежи
        kind: status
        op: partner_payment
        status: { in: response, path: data.state }
      - { http: POST, path: /gw/v2/check, name: Проверка реквизитов }
      - { http: GET, path: '/gw/v2/customers/{user_id}', name: Поиск клиента }
    errors:
      - { code: '51', title: Недостаточно средств, action: Предложить клиенту другую карту }
      - { code: '00', title: Операция одобрена, severity: ok }
    outcomes:
      # HTTP 200 и OK — успех, хотя общий признак нашёл непустое error.
      - when: { http: 200, fields: [{ path: status, equals: OK }] }
        outcome: success
      # HTTP 200 и статус ошибки — отказ с текстом из тела.
      - when: { http: 200, fields: [{ path: status, equals: error }] }
        outcome: error
        text: '{message}'
        action: Передать текст партнёру
      # HTTP 422 и OK — успех, только у этого метода.
      - method: { http: POST, path: /gw/v2/check }
        when: { http: 422, fields: [{ path: status, equals: OK }] }
        outcome: success
      # «Не ошибка»: клиента нет — штатный ответ.
      - method: { http: GET, path: '/gw/v2/customers/{user_id}' }
        when: { http: 404 }
        outcome: ignore
  - key: demo-rpc
    name: Demo RPC
    hosts: ['rpc.demo-partner.example']
    description: 'JSON-RPC 2.0, все вызовы POST на /. Ошибка: объект error с code и message'
    methods:
      - { http: POST, path: /, rpc: card.info, name: Данные карты }
      - { http: POST, path: /, rpc: p2p.transfer, name: Перевод }
    errors:
      - { code: '-200', title: Карта не найдена, action: Уточнить карту у клиента }
    outcomes:
      - method: { http: POST, path: /, rpc: p2p.transfer }
        when: { http: 200, fields: [{ path: result.state, oneOf: [NEW, PROCESSING] }] }
        outcome: pending
```
